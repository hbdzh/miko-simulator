# 双设备资源基线（2026-11-22）

开发机为 Apple M4、24 GiB 内存、macOS 27.0.1，使用工作区构建的 miko 0.11.0 测试 daemon。两台临时 AVD 均使用 `agent-lean` 配置（720×1280、2 核、2048 MiB RAM、4096 MiB 数据盘、音频关闭）和 API 36 Google APIs arm64 镜像，使用 `-gpu host`。SDK 只读，AVD 在临时目录创建。

两台设备顺序冷启动，启动完成后预热 45 秒，再每 5 秒采样一次，共六次。未开启播放器窗口、同步、脚本或主动操作应用；这是模拟器进程基线，不包含播放器画面链路成本。

| 测量 | 设备 A | 设备 B |
| --- | ---: | ---: |
| 冷启动耗时 | 21.30 秒 | 25.90 秒 |
| miko 测得的进程树内存 | 4345～4372 MiB，均值 4364 MiB | 4326～4423 MiB，均值 4344.5 MiB |
| QEMU `ps` CPU | 10.3%～80.3%，均值 27.1% | 16.8%～45.6%，均值 26.2% |

两台设备计入预算合计为 8694～8768 MiB。macOS 的 100% CPU 约代表一个逻辑 CPU；短时读数受系统和客户机后台活动影响，六个样本不能代表长期平均或峰值。内存按 miko 的进程树测量，不能直接与单进程 RSS 混用。

采样完成后，测试程序首次因 APK 路径的 JSON 类型错误而失败；当次采样已完整取得，但测试整体失败，临时模拟器随后清理。修正后单独复测：缺失 APK 按预期失败，接着两台临时设备均成功安装测试 APK，`adb shell pm path` 在两台设备上均找到测试包，设备随后正常停止。

另用两台隔离的临时模拟器通过设备中心全选，实际执行批量启动、安装测试 APK 和停止：两台均显示完成，安装后通过 `adb shell pm path` 确认包存在，停止后界面显示两台均已停止。启动间隔设置为 2 秒，记录的启动时间相差约 3.38 秒。首次 GUI 测试结束时，夹具在界面正常退出并关闭 daemon 后仍使用原连接，出现 `BrokenPipe`。修正夹具后，以一台运行中的临时模拟器再次从 GUI 正常退出：设备停止、daemon 退出和夹具均成功，临时目录已清理。

同一次复测在播放器内录制并保存手势，通过绑定键回放；测试应用记录到对应的按下、移动和抬起。通过真实播放器桥向未锁定跟随端发送输入时，远端触点在本地接管前释放，本地操作期间的远端移动和抬起未注入，本地抬起后新的远端按下和抬起均到达测试应用。这里使用测试应用和直接桥接输入，尚不代表游戏操控手感或完整同步界面的双设备验收。

另一次双设备 GUI 测试从同步器面板启用未锁定跟随：主控点击及滑动后，两台测试应用均记录到相同位置的触摸序列；跟随端本地点击只出现在跟随端，随后主控点击仍被转发。此轮未在 GUI 中同时保持两端触点，也未测试断连重连。批量启动中途取消后两台设备均显示已取消并停止；单台重试启动成功。对运行中与已停止的设备同时批量安装，前者成功、后者显示“设备未运行”；启动后者并重试安装成功。

在一台临时设备上录制两次点击和一次滑动，编辑时将首个动作等待改为 0 并删除第二次点击；重新回放时测试应用记录到保留的点击与滑动，且没有被删除的点击。以上均为受控测试应用，不代表游戏手感或复杂多点手势验收。

2026-11-23 使用同样的双设备隔离配置，复测条件流程：两台设备分别等待并定位测试应用的文本、执行点击和条件分支，同时保存节点截图与报告；缺失元素的动作在两次尝试后报错，元素等待按超时退出。另一条流程从节点截图裁取模板并找到、点击对应区域，耗时约 17 秒；这是普通测试应用画面，不代表游戏画面或实时匹配性能。等待中的流程被手动输入接管后取消，报告确认输入已释放；该场景未覆盖接管时正在按住触点。CLI 和 MCP 分别启动并完成一条简单流程。截图阶段的断线恢复有针对性离线回归测试，本轮没有在截图过程中实际断开并恢复设备。

同日打开两台播放器后，通过 macOS 窗口菜单将一台播放器移到副屏时应用发生崩溃。系统日志显示 AppKit 布局期间的 `NSInternalInconsistencyException`，调用栈涉及标题栏附件，具体原因尚未确定；因此多屏排列和播放器前后台资源对比未完成，不能据此认定资源策略验收通过。两台临时设备已停止并清理。

后续复测确认，异常原因是跨屏时标题栏附件的原点被改变；将侧边栏按钮放入尺寸固定的附件容器后，窗口生命周期回归中的跨屏移动通过，两台真实模拟器的播放器中也有一台通过系统窗口菜单移到副屏，应用保持运行。两台窗口打开后执行排列，界面显示“窗口已排列”；未独立测量窗口坐标。可视化编辑器中添加等待节点，选择两台设备并启用启动暂停和节点截图，分别单步后，两份报告均成功且各有一张截图。

同次短时采样中，两台播放器均连接，设备中心处于前台，模拟器显示静态画面，分别在保持实时和后台节省模式下每三秒采样四次。实时模式 GUI 进程 CPU 为 0.2%～2.7%、RSS 约 200.5～202.8 MiB；节省模式 CPU 为 0.1%～6.3%、RSS 约 197.0 MiB；两个桥进程 RSS 分别约 23 MiB 和 26～27 MiB。短时 CPU 读数包含切换波动，静态画面无法用于判断节省幅度。后台节省模式下，一条包含等待和点击的流程完成；未测得切回前台的画面恢复延迟，也未在此模式下重新验证同步输入。

后续在隔离设备上补测：

- 截图节点暂停时，切断实际模拟器 gRPC 连接的专用本地代理，确认流程尝试重连后恢复代理；节点成功并保存截图。本次测试发现断线还可能以 gRPC `Unknown: transport error` 或 `Cancelled: operation was canceled` 返回，现已纳入可重连错误。测试模拟的是传输断线，模拟器进程持续运行。
- 使用持续变化的测试画面和调试构建播放器，测量两次从最小化恢复到绘制新帧，分别约 572.9 和 572.7 毫秒，均未超时。此前静态画面没有可判定的新帧，测量无效。该数字不包括物理屏幕扫描输出，也不能代表所有应用场景。
- 后台节省模式下，在 GUI 中开启两台设备同步；跟随端不打开窗口，主控点击后，两台测试应用均记录了相同坐标的按下和抬起。
- 两个映射触点同时按下、各自移动并依次抬起，Android 测试应用记录到单点按下、第二点按下、双点移动、第二点抬起和最后一点抬起。
- 在一台停止的临时 AVD 中创建不实际占用 50 GiB 的稀疏文件，批量克隆时该设备因空间不足失败，另一台仍成功，界面显示失败原因和重试入口；随后删除稀疏文件。单台重试操作被自动审批拒绝，未执行。
- 组合脚本调用旧版片段后，测试应用记录到触点按下与释放；循环引用按深度上限终止。最初发现首个输入的准备耗时会压缩按住时长，修复后设置为 200 毫秒的触点在真实设备上记录约 198 毫秒。

双设备验收的临时 GUI 先退出并关闭了 daemon，随后该轮测试夹具清理时向关闭的连接写入，报 `BrokenPipe`，因此该轮测试进程整体失败；上面逐项观察到的结果保留，临时设备及目录已清理。断线与触点时长的后续单设备回归完整通过。

再次建立双设备隔离场景后，克隆空间不足的错误与单台重试入口均得到复现。删除用于模拟空间不足的稀疏文件后，按源设备文件逻辑大小加 1 GiB 预留计算，需约 3.66 GB，可用约 9.75 GB；界面重试成功并创建克隆设备。该轮夹具在界面关闭前完成设备停止与 daemon 清理，测试整体通过。

在临时设备运行的 Android 系统太空游戏画面中，截取实际画面的 `AUTO` 按钮作为模板，流程识别并点击后，游戏显示自动驾驶已启用。调试构建中这次 62×20 像素模板的流程耗时约 9 秒，仅为单次受控结果。另一款已安装游戏停在用户协议页面，本次没有接受协议。

开启节点截图的暂停流程在正常停止模拟器时被取消；重新启动后，新流程执行按键并保存截图。进一步让临时模拟器进程意外退出时，发现暂停流程没有取消；修复崩溃状态的输入所有权清理后，真实模拟器复测确认旧流程被取消，设备重新启动，新流程及节点截图均成功。取消结果附带 `input ownership changed` 错误，报告中节点结果为取消；旧流程不会自动续跑。

测试入口为 `multi_device_baseline`，默认忽略，需要显式启用并提供已安装镜像的只读 SDK：

```bash
MIKO_TEST_SDK=/absolute/path/to/sdk \
MIKO_TEST_IMAGE='system-images;android-36;google_apis;arm64-v8a' \
cargo test -p miko-daemon --features emulator --test multi_device_baseline -- --ignored --nocapture
```

这是本机双设备受控样本，不是多开容量上限、普通使用性能结论或游戏验收。后续比较播放器前后台策略时，应固定相同设备、画面、窗口可见性与采样时长。
